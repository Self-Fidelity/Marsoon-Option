## 0. 一句话结论

**后端算得很快（TTFB 2~6s），慢在响应体传输：175KB 裸 JSON 以 1~3KB/s 慢传，极端时卡死 150s+。
根因是没开压缩、没开 ETag、且疑似边算边写（chunked 无 Content-Length）。
这是当前空态的第一根因，优先级高于任何前端改动。**

## 1. 实测证据（2026-09-10 20:00~21:30，均为线上真实请求）

### 1.1 计算 vs 传输

`GET /options/dashboard?product=NQ&scope=0dte&days=1`（响应 175~179KB）连测三次：

| 次 | TTFB（后端算完首字节） | 总耗时 | 传输速度 | 结果 |
|---|---|---|---|---|
| 1 | 2.0s | 4.5s | 39 KB/s | 成功 |
| 2 | 5.7s | **150.0s** | **1.0 KB/s** | **超时中断，仅收到 151KB** |
| 3 | 2.0s | 55.8s | 3.2 KB/s | 成功 |

**结论**：后端计算只要 2~6 秒，问题在首字节之后的字节流 —— 而且会"中途停顿"，
不是稳定的慢，是**stall**。这是典型的无缓冲流式写入 + 无压缩 + 可能的小 chunk 行为。

### 1.2 压缩与条件请求：都没开

```
请求头带 Accept-Encoding: gzip, br
响应头：Server: Caddy
        Transfer-Encoding: chunked
        Vary: Origin
        （无 Content-Encoding、无 Content-Length、无 ETag、无 Last-Modified、无 Cache-Control）
```

- **没有 Content-Encoding** → 175KB 裸传；d90/close 是 880~905KB；levels 24h 是 **3.4MB**。
- **没有 ETag / Last-Modified** → 前端与 BFF 无法做 304 条件请求，每次都得整包重传。
- **只有 `Transfer-Encoding: chunked`，没有 Content-Length** → 典型的边序列化边写。

### 1.3 响应体积盘点

| 接口 | 实测体积 | 压缩后预估（gzip，按 JSON 8~10×） |
|---|---|---|
| `/options/dashboard` 0dte | 175~185 KB | ~20 KB |
| `/options/dashboard` d90 | 626~884 KB | ~70~100 KB |
| `/options/dashboard` close | 905 KB | ~100 KB |
| `/options/levels` 24h@300s | **3.4 MB** | ~350 KB |
| `/options/intraday` | 359 KB | ~40 KB |
| `/options/chain` | 281 KB | ~30 KB |
| `/options/status` | 31 KB | ~4 KB |

**开压缩一项，就能把最大的 d90/close 从 ~900KB 降到 ~100KB**，按当前 1~39KB/s 的链路，
等于把 55~150s 的请求压回个位数秒。这是收益最高的一项，且改动只在服务端。

## 2. 更新策略：现状

### 2.1 实测刷新节奏（`/options/status` 每 30s 采样，持续 3 分钟）

| scope | 刷新周期 | 实测步进 | 说明 |
|---|---|---|---|
| `0dte` | **60 秒** | `+60s` 每轮 | 三品种同步刷新 |
| `nearest` | **60 秒** | `+60s` 每轮 | 与 0dte 同快照 |
| `d30` | **300 秒（5 分钟）** | `+300s` | |
| `d90` | **300 秒（5 分钟）** | `+300s` | |
| `all` | **300 秒（5 分钟）** | `+300s` | 前端已下线该档，后端仍在算 |
| `close` | **每日一次** | 固定在 `1788987600`（9/9 16:00 Chicago） | 前一 CME 交易日 EOD |

### 2.2 现状的三个问题

**问题 A：更新节奏与前端取数节奏完全脱节。**
后端 0dte 每 60s 出新快照、d30/d90 每 300s，但前端**没有轮询**（真实数据 `refetchInterval=false`），
唯一的失效驱动曾指向一个本地采集状态端点（其版本字段恒 null）→ 永不失效（该链路已于 2026-09-10 整体删除，驱动改为 Go 派生的 `/api/options/version`）。
结果：数据陈旧不可控，且失败后不重试。详见本地方案 L1。

**问题 B：没有版本号/新鲜度端点，前端无法做脏检查。**
`/options/status` 有数据但 31KB、耗时 0.7~5.6s，不适合高频轮询。
前端需要的是**只返回 `(product, scope, unix)` 三元组的极轻端点**（几字节），才能 30s 轮询做脏更新。

**问题 C：`/options/status` 存在陈旧重复条目。**
实测 `GC/nearest` 有**两条** entries：一条是新鲜的 `1789046820`（9/10 13:27Z），
另一条停留在 `1788974940`（9/9 17:29Z），且**持续存在、不淘汰**。
当前 BFF 靠 `sort by unix desc` 取第一条侥幸正确，但这是定时炸弹：
一旦排序或过滤条件变动，就会解析到 20 小时前的合约。
**需要后端清理陈旧条目，或提供明确的 `is_current` / `checked_at` 过滤位。**

### 2.3 目标态

```
后端：快照生成 → 【预序列化 + 压缩缓存】 → 版本表 (product, scope, unix)
                          ↓                          ↓
                   大响应直接吐缓存字节          极轻 version 端点（几字节）
                          ↓                          ↓
前端：30s 轮询 version → unix 变了才拉大响应 → 304/缓存命中则零传输
```

## 3. 优化项（按 收益 × 可行性 排序）

| # | 优化项 | 归属 | 收益 | 依赖 |
|---|---|---|---|---|
| **S1** | **开启 gzip / br 压缩** | Caddy 或 Go | **极高** | 无 |
| **S2** | **预序列化 + 一次性写出（带 Content-Length）** | Go | **极高** | 无 |
| **S3** | **快照级响应缓存（Buffer 复用）** | Go | 高 | S2 |
| **S4** | **ETag / Last-Modified + 304** | Go | 高 | S3 |
| **S5** | **极轻 version 端点** | Go | 高 | 无 |
| **S6** | **接口裁剪 / 分页 / 降采样** | Go | 中高 | 前端契约确认 |
| **S7** | **清理 status 陈旧条目 + `is_current` 位** | Go | 中 | 无 |
| **S8** | **WebSocket 增量推送**（远期） | Go | 中 | S3/S4 之后 |

### S1 开启压缩（最高优先级）

- **做法**：Caddy 侧加 `encode gzip br`（对 `application/json` 生效），或 Go 侧用 `gzip.Writer` /
  `klauspost/compress` 直接压。建议**服务端压**，避免 Caddy 对每个请求重复压缩。
- **注意**：配合 S3 缓存时，压一次存起来，后续请求直接吐压缩字节，CPU 也省了。
- **验收**：`curl -H "Accept-Encoding: gzip" -D - -o /dev/null` 应看到 `Content-Encoding: gzip`，
  且 `size_download` 降至 ~100KB（d90）/ ~20KB（0dte）。
- **预期**：这是唯一能直接把 55~150s 请求压回个位数秒的改动。

### S2 预序列化 + 一次性写出

- **问题**：现在只有 `Transfer-Encoding: chunked`、无 `Content-Length`，且传输中会 stall，
  高度怀疑是 Go 的 `json.Encoder` 边 encode 边 flush（每个 chunk 一次 syscall / 小包写出）。
- **做法**：先 `json.Marshal` 到 `bytes.Buffer`（**这就是服务端的 buffer**），
  拿到完整字节后设置 `Content-Length`，再一次性 `w.Write(buf)`。
- **收益**：消除流式 stall；顺带得到长度和稳定哈希（S4 的 ETag 可直接用内容哈希/版本号）。
- **验收**：响应头出现 `Content-Length`；`time_starttransfer` 与 `time_total` 差距应显著缩小。

### S3 快照级响应缓存（Buffer 复用）

- **现状**：d90/close 每 5 分钟才更新一次快照，但**每个请求都重新序列化 900KB**。
- **做法**：快照生成后，把"原始 JSON 字节"和"gzip 后字节"各存一份，按
  `(product, scope, snapshot_unix)` 做 key；请求命中直接吐缓存，不进业务逻辑。
- **收益**：命中路径从"计算 + 序列化 + 慢传"变成"内存拷贝 + 一次 write"，
  对 5 分钟才变的 d30/d90 尤其明显；也让 S4 的 ETag 变得零成本。
- **内存估算**：三品种 × 4 scope × (原始 ~900KB + gzip ~100KB) ≈ 12MB，完全可接受。

### S4 ETag / 304

- **做法**：ETag 直接用 `"<snapshot_unix>"`（内容随快照变化，语义正确且零计算）；
  响应加 `Cache-Control: no-cache`（允许缓存但必须回源校验），前端带 `If-None-Match`。
- **收益**：30s 轮询在同一快照版本内返回 **304 + 空体**，不再传 175KB~905KB。
  这一项与本地方案 L1（脏更新）叠加后，非更新时刻的带宽消耗接近零。
- **验收**：`curl -H 'If-None-Match: "1789047000"'` → `304` + `size=0`。

### S5 极轻 version 端点

- **需求**：`GET /options/version`（或 `/options/status?light=1`），
  返回体 < 1KB：

  ```json
  { "entries": [{ "product": "NQ", "scope": "0dte", "unix": 1789047000 }, ...] }
  ```

- **理由**：让前端能做**脏更新**（版本号变了才拉大包），而不是定时全量轮询。
  当前 `/options/status` 31KB、0.7~5.6s，不适合 30s 高频轮询。
- **本地侧已备好对接方式**，见 `../frontend/本地侧优化方案.md` L1。

### S6 接口裁剪 / 分页 / 降采样

- `levels` 24h@300s 返回 **3.4MB**，是全站最大响应，也是最容易撞超时的接口。
  建议支持 `from/to` 分页或 `max_points` 降采样参数。
- `dashboard` 的 `heatmap.cells` 在 d90 时达 1900 格；建议支持按 `window_pct` 之外的
  价格窗口显式裁剪。
- ⚠️ 涉及数据契约，改动前需与前端确认 `src/api/options.ts` 的类型定义。

### S7 清理 status 陈旧条目

- 实测 `GC/nearest` 存在两条 entries，其中一条停留在 9/9 17:29Z 且长期不淘汰（见 §2.2 问题 C）。
- 建议：同一 `(product, scope)` 只保留当前条目；或增加 `is_current: bool` / `checked_at` 供消费方过滤。
- 这是**正确性**问题，不是性能问题，建议与 S1 同期修。

### S8 WebSocket 增量推送（远期）

- 现在已有 `wss://<base>/ws`（K 线）。远期可让 0dte 快照走推送，
  彻底免掉 60s 轮询。但**必须在 S1~S4 之后**再做 —— 在带宽问题没解决前上推送，只是把问题换个地方。

## 4. 关于"buffer"（服务端视角）

| 形态 | 说明 | 对应项 |
|---|---|---|
| **序列化缓冲** | 先 `json.Marshal` 到 `bytes.Buffer`，再一次性写出，避免边算边 flush 造成 stall | **S2** |
| **响应缓存** | 快照级缓存已序列化的字节（含 gzip 版），请求命中直接吐 | **S3** |
| **写入缓冲** | `bufio.Writer` + 显式 `Flush`，避免 Nagle/小包 | S2 附带 |

**注意**：服务端的 buffer 不是为了"等数据凑齐"，而是为了**避免把内部计算节奏暴露到网络上**。
当前 chunked 无长度、中途 stall 的表征，几乎可以确定是序列化与写网络耦合在一起了。

## 7. 补充需求与优先级刷新（2026-09-11，对应前端"首屏提速"改造）

前端已于 2026-09-11 落地本地快照持久化（IndexedDB）+ 调度器状态跨会话恢复 + 三处口径/扇出修复
（细节：`docs/architecture/K线与期权数据周期管理与防堵塞设计.md` §九）。落地后**刷新/重开页面在快照未变时零重请求**，
服务端压力已显著下降；但只要快照有变化，单次请求仍要承担 25~60s 重聚合与 900KB 级裸传——以下需求仍然成立，
本节按当前收益重排优先级（与 §5 清单并存，编号沿用 S1~S8）：

| 优先级 | 需求 | 说明 |
|---|---|---|
| P0 | **请求路径零重算**（S3 的彻底版） | 所有读请求改 O(1) 快照读取（预计算 + 快照缓存）。实测 options_only 常态 21~58s、dashboard 2~28s、chain 6~20s，且 intraday/chain 0dte 长尾偶超 55s 突破前端超时——请求触发全量重算在本仓视为 bug |

| P2 | **WS K线链路审查** | ① 有无应用层心跳/ack；② 重连后订阅是否自动恢复；③ 半开连接最大静默时长（实测 4 分钟无感知）；④ `final` 标记在 REST tail 是否同样下发；⑤ candles-ws ticket 明文 token。详见 `docs/architecture/K线与期权数据周期管理与防堵塞设计.md` §六 |
| **P1（正确性）** | **0DTE 开盘后墙位倒挂（PW>CW）口径修复** | 实测 NQ 0DTE 价格大幅波动后 CW/PW 倒挂且数小时内剧烈漂移；已验证非前端问题、非计算错误，根因是"墙=全链 GEX 极值档（无现价侧约束）+ OI 延迟 × 盘中 mid 反解 IV 的时间错配"。最小可行解：输出侧加墙位相对现货位置/倒挂标记；深化：OI 延迟质量位、夜盘 IV 反解质量、聚合 flip 口径、0DTE=16:00 ET 到期口径、OI 墙 moneyness 过滤。**详见本文 §8（含实测数据、复算过程、R1~R6 需求与验收）** |

**验收基准**：任意读接口在快照未变时 P95 < 1s（缓存命中）；快照变化后首请求 P95 < 10s；响应带 Content-Encoding 与 ETag。

## 8. 0DTE 开盘后墙位倒挂（PW > CW）问题定位与需求（2026-09-11 实测）

> 本节为**正确性/口径问题**，与 §1~§7 的性能问题独立，但同样只能 Go 侧解决。
> 前端已完整排查并排除本地责任（BFF 纯透传、ViewModel 只取字段、无墙位计算代码，已删的
> `barchart-greeks.ts` 本地引擎不参与现行链路）。以下全部结论基于对线上
> `mws.marsoon.cn` 原始响应的抓取、逐档重算与时间序列回溯，可复现。

### 8.1 现象

0DTE scope 在**开盘前夜盘/早盘大幅波动后**，`call_wall` 与 `put_wall` 出现**倒挂**
（PW 价位高于 CW），且墙位在数小时内剧烈漂移。前端 05/06/09 面板把墙位作为
"阻力/支撑"水平线展示，倒挂直接破坏该语义，用户侧表现为"算法错了"。

实测快照（2026-09-11T13:25:00Z，NQ 0DTE，三品种同分钟）：

| 品种 | spot | CW | PW | Flip | 形态 |
|---|---|---|---|---|---|
| NQ | 29427.875 | **29380** | **29500** | 29214.79 | ❌ 倒挂（PW 高于 CW，spot 骑在两墙之间） |
| ES | 7666.125 | 7700 | 7650 | 7668.17 | ✅ 正常 |
| GC | 4393.6 | 4400 | 4350 | 4387.12 | ✅ 正常 |

`/options/levels` 时间序列（NQ 0DTE，timeframe=300）显示**同一天 10:30–10:40 UTC
还是 PW=29000 < CW=29380 的正常形态**，10:40→13:25 之间价格上行约 250 点后倒挂——
即倒挂随价格移动出现/消失，非持续脏数据。

### 8.2 验证过程与结论（前端侧已完成，后端可复算）

1. **数据新鲜度** ✅：snapshot_unix 与 status checked_at 差 ~1 分钟。
2. **内部一致性** ✅：用 `heatmap.cells` 逐档重算三品种
   `argmax(call_gex)` / `argmin(put_gex)`，与 `market_state` / `summary` / `levels`
   三处下发的墙位**完全一致**——后端计算忠实，不存在序列化/聚合丢错。
3. **希腊字母量级** ✅：以 Black-76 独立复算，NQ 距到期 6.58h、IV≈25% 时 ATM gamma≈0.00198，
   推得每张 GEX≈3.42e5，实测 3.07~3.22e5/张，吻合。
4. **倒挂档的构成**：NQ PW=29500 仅 **put_oi=161**（全链 put OI 王是 28800 的 768 张）——
   小 OI 档凭贴近现价的 gamma 峰值夺冠；CW=29380 为 call_oi=434。
   两档 quality_flags 均为 0。
5. **结论**：**不是算错，是口径使然**——详见 8.3。但"口径使然"不等于"没问题"，
   见 8.4 的分层需求。

### 8.3 算法链路溯源（文档 + 实测双重确认）

现行链路（`Go期权API对接与改进方案.md` §3.2、`ClickHouse期权改造实施设计.md`）：

```
Databento 1min 快照：C/P bid/ask/last + OI（官方延迟发布）+ 期货价
  → Calculator.Calculate：mid=(bid+ask)/2 → Black-76 反解 IV → gamma/delta
    （准入门槛：默认 OI≥10、价差检查、报价陈旧性检查、IV 反解合法性）
  → GEX = OI × Γ × F² × 乘数 × 1%（call 正 / put 负）
  → CW = 全链 argmax(call_gex)；PW = 全链 argmin(put_gex)；Flip = 净 GEX 变号点
```

**两个结构性的口径事实**：

- **CW/PW 是"全链 GEX 极值档"，不是"现价上方最近阻力 / 下方最近支撑"。**
  算法对现价两侧**没有任何约束**，倒挂是 argmax/argmin 的合法输出。
- **OI 与 IV 时间错配**：OI 取前一结算的官方持仓（盘中静态），gamma 由盘中 mid
  实时反解。隔夜 gap 后，等于"昨天的仓位分布 × 今天的价格结构"，墙位随价格穿仓
  密集区而剧烈漂移（NQ 的 PW 三小时内 29000→29500）。

这两个事实叠加：只要现价走进 OI 密集区（0DTE  strike 间距小、gamma 峰值尖锐，
几小时即可发生），倒挂必然出现。前端红线是零计算、零修饰，**无法在展示层修复**。

## 9. GC 期权层空白实例（2026-09-12 实测）——S1 压缩的具象证据

用户实测：06 面板挂「期权OI分布·前日EOD / 期权成交量分布·0DTE / 期权水位·0DTE」三个指标，
**黄金全部空白但 K 线与期货成交量正常**（ES/NQ 同配置正常）。前端完整排查结论：

1. **前端逻辑无错**：用线上真实 payload 回放整条消费链（BFF 模拟 + 真实 ViewModel 编译件），
   三个层对 GC 全部应渲染（水位 4 条位置线、OI 分布 40 行、成交量分布 72 行）。
2. **三个层恰好共用重车道，而 K 线走快车道**：水位=intraday detail、OI 分布=dashboard close、
   成交量分布=0dte-volume-profile，全部经 heavyLane；K 线 bars_only/WS 不过信号量。
   GC 响应在 1~3KB/s 无压缩链路上传不完 55s 上游预算 → 三个请求系统性 502 → 层空白、K 线完好。
3. **GC 实测体积**（2026-09-11 夜盘，无压缩裸传）：

| 端点 | 实测体积 | 55s 预算所需最低速度 | 实测速度 | 结局 |
|---|---|---|---|---|
| `dashboard?scope=close`（GC, underlying=GCV6） | **772 KB** | ≥14 KB/s | 1~3 KB/s | ❌ 必超时 |
| `intraday`（GC 0dte，旧含 levels 轨迹） | **170 KB**（1164 条 levels 占 ~150KB） | ≥3.1 KB/s | 1~3 KB/s | ⚠️ 边缘超时 |
| `0dte-volume-profile`（GC 2h） | **208 KB** | ≥3.8 KB/s | 1~3 KB/s | ⚠️ 边缘超时 |
| `intraday?bars_only`（GC） | ~15 KB | ≥0.3 KB/s | 1~3 KB/s | ✅ 正常（K 线不受影响的根因） |

4. **前端已做的缓解**（2026-09-12 落地，治标）：
   - BFF intraday 裁剪 `levels[]`（全仓确认无消费方，唯一消费方是 /options/levels 端点的旧仪表盘页），
     GC intraday 170KB → **约 2KB**，水位可靠性不再受传输制约；
   - `mergeDashboardCurrent` 改新鲜度优先，修 dashboard 旧快照回盖新 current 的水位回跳。
5. **仍受制于传输的**：OI 分布·前日EOD 需要完整 close 快照（772KB，gzip 后约 80~100KB 可 10s 内传完）。
   **S1（gzip/br）+ S2（预序列化+Content-Length）落地前，GC 的 close 档在慢链路上不可用**；
   这不是前端再调超时能根治的——把 55s 预算加到 110s 也只是"有时能过"。

**附带确认的两个 GC 后端数据问题**（与 §8 同类，需 Go 侧知悉）：

- `dashboard?scope=close` **不传 underlying 时**返回 `GCZ7`（2027 年 12 月合约，价 4624.7）作为
  market_state，`expected_move ±1186`（26%）；传 `underlying=GCV6` 则正常（4450/4450/4352）。
  即 close 档在多合约月份的 argMax 选择会选到远月——前端 BFF 始终传 underlying 所以不受影响，
  但这是 §8 R-类口径问题的又一个实例（heatmap/levels 的 argMax 混合）。
- GC 的 status 里 `d30`/`d90`/`all`/`close`/`nearest` 各有 2~10 条不同 underlying 的 entries
  （GCV6/GCZ6/GCG7/...），与 ES/NQ 单合约结构不同；任何"按 scope 取第一条"的消费方都会对 GC 踩坑。

## 10. 方案确认请求（2026-09-12）：定时预计算 + 压缩传输

**请后端明确回答：读路径能否改为「Worker 定时计算 → 预序列化 + 压缩缓存 → 读请求 O(1) 吐字节」？**

这是把 §3 S1~S4 与 §7 P0「请求路径零重算」合并后的完整目标态，也是前端侧所有缓解措施（超时放宽、双车道、本地持久化、payload 裁剪）之后的**最终根治方案**。请按下列要点确认可行性与排期：

1. **定时计算（替代请求触发计算）**：按现有产出节奏（0dte 60s / d30·d90 300s / close 日结）由 Worker 定时生成各 `(product, scope)` 快照，写入快照缓存；
   读请求不再触发任何重算。——若排期困难，请给出分阶段路径（先 0dte 再 d30/d90 再 close）。
2. **压缩传输**：快照字节在生成时即 gzip/br 压缩存储（压一次存起来），响应头带 `Content-Encoding`，
   命中路径零压缩 CPU。——这一项与第 1 项相互独立，**即使定时计算暂不做，压缩也可以先上**，请先答复这一项。
3. **读路径 O(1)**：命中路径 = 一次 map 查找 + 一次 write，P95 < 1s（§7 验收基准已列）。
4. **304/版本化**：ETag 用 `snapshot_unix`，消费方脏检查逻辑前端已全部备好（§2.3 目标态图）。

**为什么必须确认**：截至 2026-09-12，前端已把本仓能做的全部做完（超时链对齐、双车道、IndexedDB 持久化、
intraday 无效载荷裁剪、BFF 会话缓存），但 §9 GC 实测证明——只要读请求还触发重算、只要链路还裸传，
**大载荷档（close 772KB~905KB）在慢链路上就是不可用**，与前端怎么优化无关。
此问题不解决，看板的 close（EOD）档、GC 品种、以及任何网络抖动的时刻，都会持续出现"指标空白但 K 线正常"。

**请回复**：① 方案是否可行；② 各项排期；③ 是否需要前端配合的契约变更（如需，请指到 `src/api/options.ts`）。

## 11. 前端静态资源与首载传输（部署/反代侧，2026-09-12）

前端代码侧节流已于 2026-09-12 落地（面板懒加载、无效载荷裁剪、版本驱动零重请求）。
以下剩余项在**部署层**，若前端站点经 Caddy/nginx 反代（或与 Go 服务同机部署），一次配置两侧受益：

1. **静态资源 gzip/br 压缩**（收益最高）：当前实测全站静态 JS 387KB（gzip），
   `/_next/static/*` 的 `.js/.css` 与 `/teaching-content/*.html`（7 页共 1.7MB，压缩后约 200KB）
   在反代上开启 `encode gzip br`（Caddy）或 `gzip_types text/css application/javascript text/html`（nginx）。
   若裸用 `next start` 且无反代，public/ 下的大 HTML 是**不压缩直出**的——教学页首次打开会明显慢。
2. **长缓存头**：`/_next/static/*` 带内容哈希，可 `immutable, max-age=31536000`；
   `/teaching-content/*` 已由前端 `next.config.ts` headers 下发 1h+SWR，反代不要覆盖掉。
3. **HTTP/2 或 HTTP/3**：多 chunk 并行下载（当前首载 9~10 个 JS 文件），h1.1 串行会放大首屏时间。
4. **（可选）CDN/边缘缓存**：静态资源走 CDN，源站只承担 API 压力——对"服务器资源紧张"是釜底抽薪。
5. **（远期，可选）多 scope 聚合端点**：新用户冷启动首波要按 scope 各拉一次快照
   （前端已做每拍≤2 + 相位错开 + 主档优先）；若提供一个 `scopes=close,0dte` 一次返回的端点，
   冷启动往返数可减半。优先级低于第 1 项。

**给后端的验证方法**：改完后 `curl -H "Accept-Encoding: gzip" -D - -o /dev/null https://<前端域名>/_next/static/chunks/<任一js>`
应看到 `Content-Encoding: gzip`；`size_download` 约为原始值的 1/4~1/3。
