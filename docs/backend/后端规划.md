> 4. §5 缺口清单的落地情况：#1 交易日历已由后端提供（`calendar: "CME-ES-NQ-GC-2026"`，随 `close_reference` 下发）✅；#5 登录/权限已实现（邮箱 OTP + HttpOnly Cookie，见 `../interface/登录与会话.md`）✅；#4 数据新鲜度告警 ⚠️ 仍缺（`/options/status` 提供 `checked_at`/`source_unix`，但没有告警）；#3 历史回填 ✅ 部分可用（dashboard 支持 `asof`）；#7 文档纪律 ✅ 本轮已补 `../interface/Go后端接口清单.md`。
> 5. **新增的突出问题（本文未覆盖）**：后端响应耗时极不稳定（`/options/levels` 实测 0.8s~107s）、单响应可达 3.4MB，远超 §2 的"dashboard ≤100KB / bars ≤2 天"预算。这是当前最需要后端治理的一项。

## 0. 先定量级（决定一切取舍）

| 维度 | orderflow（参照系） | 本产品 |
|---|---|---|
| 数据粒度 | tick 级逐笔/委托/十档 | **1 分钟快照 + 1min K线**（用户明确不要深度数据） |
| 标的 | 全市场股票 | 3 个品种（NQ/ES/GC） |
| 日增量 | 千万行级 | 百万行级原始、**预计算后千行级** |
| 前端刷新 | 亚秒 live push | 60s 轮询 |

结论：orderflow 的**存储分层、并发闸门、补洞机制、诊断纪律**要抄；它的 **WebGPU、Worker/SAB、Arrow IPC、Parquet 数据湖**不抄——那是 tick 级量级的解法，我们用上是过度工程。

## 1. 写路径（vendor → 预计算表）

```
Databento/CME ──采集──→ ClickHouse 原始层 ──1min批计算──→ 预计算层
(definitions/statistics/   trades(TTL 30d)              option_marks
 trades/quotes)            quotes(TTL 7d)                gex_snapshot
                           instruments                   levels_ts
                           settled_oi(永久)              bars_1m(物化视图, 永久)
```

### 1.1 采集（借 orderflow 的纪律）

- **水位 + 幂等**：每品种维护 `ingest_watermark(product, channel, ts)`；重跑同区间不产生重复行（instrument+ts 去重，ReplacingMergeTree 或写入前去重）。
- **断线补洞**（借 Binance pipeline 模式）：实时流断了不硬撑，恢复后用 REST/批量接口回补缺口区间，水位连续才算完。
- **并发闸门**：对上游的并发请求设上限（orderflow 用 CH max 4；我们对 Databento 同样设 ≤4），批量历史回填与实时采集**互斥让路**（回填时实时优先）。
- **合约主数据**：`instruments` 每日全量刷新；**盘中新挂 strike**（0DTE 尤其常见）要能即时插入，不等日终——这是期权和股票订单流的一个本质差异。

### 1.2 批计算（每 1 分钟一轮，幂等）

1. 取最新 quotes → Black-76 反解 IV、算 Greeks（红线：期货期权不用 Black-Scholes，见技术架构 §4.3）。
2. 按 strike 聚合 GEX（符号假设集中在此，业务逻辑 §4）。
3. 提取 walls / flip / key gamma → 写 `levels_ts`。
4. 同一 `ts` 重算 = 覆盖写，天然幂等；失败整轮重试，不写半成品。

### 1.3 OI 双轨（审计发现 5 的落地）

- `settled_oi`：交易所隔夜结算，每日一次回填，永久保留。
- 盘中 `gex_snapshot.*_oi` = 昨结 + 盘中净成交估计，`quality_flags` 置位"估计"；次日结算后回填修正。
- 前端永远不知道这个差别。

## 2. 读路径（预计算表 → API → 前端）

原则（与 orderflow 一致）：**查询只读本地预计算层，任何请求路径上不现场 derive**。

- **Range-only**：所有接口必须带 `[from, to)`；禁止"全量下载"型 API。
- **响应预算**：dashboard ≤100KB gzip（cells 用 `window_pct` 窗口限 strike 数）；levels 60min×12 桶；bars 一次 ≤2 天。
- **缓存**：API 进程内缓存（dashboard 30s / levels 60s / bars 60s）+ `ETag`，304 命中零序列化；响应 gzip。
- **降级纪律**（Marsoon 红线）：缺字段传 `null`，前端不绘制，绝不降级为 0；`quality_flags` 位掩码原样透传。
- **stale 判定**：前端拿 `observed_max_unix` 与本地时钟比对，超阈值显示 stale 标记（Marsoon 已有此状态位）。

## 3. 传路径（传输通道）

**当前（够用，先做这个）**：全部走 REST JSON 轮询——

| 通道 | 节奏 | 载荷 |
|---|---|---|
| `/options/dashboard` | 60s | summary + heatmap 窗口 |
| `/options/levels` | 60s | walls/flip 迁移 |
| `/options/underlying-bars` | 60s | 简易K线 |
| `/options/heatmap` | 60s | 全量 cells |

**演进（真需要时才做）**：若日后 K线或 flip 要亚分钟级，再上**本机 WebSocket**，协议直接借 orderflow live-session 的成熟语义：**snapshot + bar_patch 增量、upsertTail 单写、禁止 per-tick setData**（per-tick 直接驱动 React 是 orderflow  ban list 里的已知翻车点）。

**不抄**：Arrow IPC / WASM 计算通道 / gzip 二进制——orderflow 自己也是在 tick 级量级才上的，我们的载荷小两个数量级，JSON+gzip 到顶。

**安全边界**（orderflow 硬规则，直接继承）：浏览器只连我们的 API；**永不直连 vendor、永不直连 ClickHouse**；密钥只走环境变量，不进源码/文档/日志/前端。

## 4. 运维与稳定性（借 BACKEND_STABILITY 的教训）

- **进程**：docker-compose `restart: unless-stopped`；四容器（clickhouse/api/ingestor/compute）各自健康检查。
- **诊断端点**（借 `/live/diag` 模式）：`/health`（存活）+ `/diag`（数据新鲜度 = 当前时间 − observed_max_unix、采集水位、最近一轮批计算耗时、quality_flags 计数）。前端状态栏的数据时间戳也从这里来。
- **Windows 开发坑**（orderflow 实踩）：数据目录路径**不要带空格**（它的 DATA_DIR 空格导致过后端"开着却掉线"）；开发机改了代码记得重启进程，别拿旧进程手测。
- **备份**：`settled_oi`、`instruments`、`bars_1m`、`gex_snapshot`、`levels_ts` 是永久数据，每日备份；trades/quotes 原始层有 TTL 不备份。

## 5. 缺口清单（对照自查，"还有没有漏的"）

| # | 缺口 | 说明与建议 |
|---|---|---|
| 1 | **交易日历/时区** | CME = America/Chicago（有夏令时切换）、周日 17:00 开市、节假日/半日。0DTE 判定、K线 sesion 边界、前端"盘中/非盘中"降频全依赖它。需要一张 `calendar` 表，此前所有文档都没覆盖 |
| 2 | **合约主数据生命周期** | 日内新挂 strike、合约乘数/tick 变更、到期摘牌。§1.1 已补 |
| 3 | **历史回填** | 教学页和复盘需要"历史上某一天"的完整快照。采集器要支持按日回填模式（orderflow 的 day-stage + 断点续传模式可直接借） |
| 4 | **数据新鲜度告警** | 批计算挂了，前端只会看到 stale 标记，没人知道。`/diag` + 一个简单告警（邮件/webhook） |
| 5 | **登录/权限** | Marsoon README 明确"未处理登录"。个人/内网用可以先不管，**对外之前必须补**——列在这里防忘 |
| 6 | **部署环境定义** | 开发在 Windows、生产建议 Linux 单机。docker-compose 一套两处跑，差异只许出现在 env 文件 |
| 7 | **文档纪律** | 借 orderflow 的路由表模式：本目录 4 份文档已有分工，日后新增子系统（如回填管线）→ 新建一份文档 + 只在 README 加一行，不搞第二套索引 |

## 6. 落地顺序

1. ClickHouse 建表（§1 全套）+ instruments/calendar 每日刷新。
2. 采集器：trades/quotes/OI 三通道 + 水位幂等 + 补洞。
3. 批计算：Black-76 → GEX → walls/flip（单元测试钉住解析解）。
4. FastAPI 只读层 + ETag + `/health` `/diag`。
5. 前端接通（技术架构 §7 阶段 4），K线接口解锁 06。
