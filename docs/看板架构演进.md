# 看板架构演进（多窗口 · 解耦与联动）设计文档

> 创建：2026-09-02
> 性质：**总纲文档**，指导后续多轮迭代；不是单面板需求
> 背景问题：① 周期 scope 全局单选卡死，无法同屏对照多周期；② 单页 grid 多面板的滚动脱钩/手势串扰（面板滚到底页面跟着跑、拖拽冲突）；③ 目标形态：分窗自包含 + 窗口间可解耦可联动（Bloomberg/IBKR Mosaic/TradingView 多图布局的成熟范式）。

## 一、目标架构

**窗口三要素自包含**：每个窗格持有自己的 `品种 × 周期scope × 面板类型`。例：窗 A = NQ·0DTE·日内图，窗 B = ES·90D·热力图，同屏对照互不干扰。

**链接组（Link Group）**：窗口默认解耦；可加入颜色标记的链接组实现联动——

- 品种联动：组内一窗切品种，同组跟随，各自保持自己的周期与面板类型；
- 周期默认**不**进链接维度（联动需求弱）；
- "一键全切"的旧全局行为 = 全部窗口同组，功能不丢失。

**滚动与手势隔离**：每窗 `overscroll-behavior: contain` 锁死滚动冒泡；面板内手势（K 线平移、grid 拖拽手柄）统一规范、互不抢占。

**布局持久化**：现有 grid 布局自动保存扩展为"每窗三要素 + 链接组"全量配置持久化（localStorage）。

## 一·五、三维联动模型（已定稿 2026-09-03）

三个维度性质不同，联动机制分开设计：

| 维度 | 本质 | 形态 | 联动机制 |
|---|---|---|---|
| 标的（ES/NQ/GC） | 全局上下文 | 单选/窗口 | **捆绑按钮（链接组）**：窗口头部开关，开=进组，组内一切全跟随；默认全开（等效旧全局行为） |
| 期权周期（close/0dte/d30/d90/all） | 仓位聚合口径 | **线条类面板多选叠加；表格/矩阵类单选** | 标的级联动 + 解耦语义（2026-09-04 定稿）：联动=跟随总控、解耦=冻结当时快照窗内自治，📌 scopePinned 已废除 |
| K线周期（1m~1h） | 价格观察粒度 | 单选/窗口 | **无联动，纯窗口私有**，随布局持久化 |

**期权周期的分形态规则**：

- 线条类（06 日内、10 期限结构、07 微笑）：周期多选、同图叠加。视觉编码**两维正交**——颜色=语义（CW 绿 / PW 红 / FLIP 品牌色 / SPOT 亮蓝），线型=周期（0D 实线 > 30 短虚线 > 90 点线 > RTH 低密度虚线），右轴徽标沿用前缀体系（`0D·CW`/`30·CW`/`90·CW`/`RTH·CW`，PC 层为描边虚框牌）。
- 表格/矩阵类（09 链、05 热力图、08 拆分）：单选，默认跟随总控，解耦后冻结当时快照、窗内自治。

**已识别的坑与设计规则（迭代时必须遵守）**：

1. **线型冲突**：禁止用语义维度占用线型（FLIP 的虚线改由"语义色+品牌色"承担，或 FLIP 固定为 dashed 而周期用宽度/透明度区分——实现时二选一并写死注释，两维绝不混用）。
2. **徽标爆炸**：上限 3 周期 × 4 位 = 12 牌，规则：主选中周期（多选数组第一项）出全套牌，其余周期只出 FLIP 牌；同价聚类合并。
3. **y 域防撑扁**：y 域只跟随可视窗口蜡烛 + 主周期墙；其余周期的墙超出范围不撑域，贴边画方向箭头+数值。
4. **空态混选**：多选含空周期（close 未接入/非 0DTE 日）静默跳过、不造线，图例对应项灰显。
5. **迁移折线只画主周期**（多选第一项），避免轨迹糊图。
6. **回放成本线性**：intraday 游标按 scope key 各算一份，叠加周期数 ↑=重算成本线性 ↑，多选上限 3。
7. **联动尖刺**：切标的时组内 N 窗同时 refetch——服务端 R1 缓存兜底，前端不做特殊处理，记录为观察项。
8. **📌/捆绑状态必须进布局持久化 JSON**，否则还原错乱。

**契约改造**：线条类接口的 scope 参数改数组（`scope=0dte,d90`），响应按 scope 分段；缓存 key 仍为单 scope（前端多 key 并发取、React Query 去重），服务端零新增计算（R1 扇出已覆盖全组合）。

## 二、性能与稳定性设计（硬需求，大行情下不得出瓶颈）

### 核心原则：计算时机从"请求拉动"改为"数据推动"

大行情的风险点：价格波动剧烈 → 面板高频刷新 → 若计算由请求触发，N 窗 × M key 的并发重算会打满单进程 Node。**解法是把计算挪到数据入库的那一刻，且只做一遍**：

### R1. ingest 扇出预算（服务端，最高优先级）

- 每轮快照 POST `/api/ingest/barchart` 入库后，**立刻主动计算 3 品种 × 4 scope（close 空态除外，实际 3×3=9 个 key）的聚合分析**，结果写入内存缓存（key = `capturedAt|product|scope`）。
- 所有 API 路由**只读缓存**，任何情况下不在请求路径上做 Black-76 全链重算；缓存 miss 时返回 `has_data:false` 空态 + 触发后台补算，**绝不在请求里同步算**（宁可短暂空态，不可阻塞事件循环）。
- 单轮全链分析实测为秒级内的固定成本，9 个 key 串行扇出可接受；若未来 serie 数/档位暴涨，扇出迁 worker_threads。

> ⚠️ **REST / WS 入口差异（后续开发 AI 必读）**：当前数据入口是 **REST 轮询**——采集器 15min 一次 POST `/api/ingest/barchart`，一轮一个快照，扇出时机天然清晰（每 POST 一次扇出一次）。未来 Databento 接入后是 **WebSocket/流式推送**，数据连续到达（1min bars、tick 级），"入库"不再是一个离散事件：
>
> - **扇出必须挂在"数据落地事件"抽象层上，而不是挂在 HTTP 路由里**——设计时把 ingest 处理函数抽成 `onSnapshotLanded(snapshot)` 之类的入口无关函数，REST 路由和 WS 消费者都调它。写代码前先确认扇出逻辑没有和 POST 路由耦合。
> - **WS 下扇出要节流**：流式数据可能每秒甚至每 tick 到达，绝不能每个事件都全量扇出 9 个 key——按快照版本节流（如每 N 秒/每 N 个事件合并扇出一次，或按品种 dirty 标记延迟批量算）。REST 轮询时代"一轮=一扇出"的假设在 WS 下不成立。
> - **capturedAt 记忆化的版本语义**：WS 增量更新下"快照版本"不再天然存在，需要引入显式版本号（单调递增），缓存 key、前端轮询对齐（R3）、游标（R2）都依赖这个版本语义，接 WS 时一并设计。
> - **断开/乱序**：WS 流有断线重连、消息乱序问题，入库前要做序列校验与缺口检测（Databento 有序列号），REST 轮询没有这个问题——不要把现有"每行快照自包含完整"的假设带进 WS 设计。

### R2. key 空间有界 + LRU 兜底

- 分析缓存 key 上限 = 品种数 × scope 数（当前 9），**有界**；intraday 回放缓存同理（已有 24 key LRU 游标）。任何"按请求参数无限组合"的缓存 key 设计都是 bug。
- 同 key 并发请求合并（in-flight 去重，已实现，保持为所有新路由的默认模式）。

### R3. 前端请求收敛

- React Query 同 key 天然去重；**轮询对齐**：同一快照版本（capturedAt）下各面板 refetch 共享同一 Promise，避免 7 面板 × 各自 60s 定时器错相位造成的请求尖刺——实现为面板数据层统一走一个"快照版本感知"的 queryClient 配置（refetchInterval 不变，但 staleTime 锚定 capturedAt）。
- 面板独立 scope 后，前端 key 数上界 = 窗格数 × 每窗 key 数，同样有界（窗格数人为可控）。
- 后续可选：SSE/WebSocket 服务端推送替代轮询（数据到 → 推 capturedAt 版本号 → 前端按需拉取），大行情下流量和延迟都更优；本轮记录备查。

### R4. 降级与背压

- 任何计算超时/失败：前端显示带时间的陈旧数据 + "数据延迟"角标（stale-while-revalidate），不白屏不报错弹窗。
- 服务端对每个 key 记录"上次计算耗时"，超过阈值（如 2s）打警告日志——大行情数据量膨胀时我们能从日志先看到趋势，而不是从用户抱怨。

### R5. 禁止项（写代码红线）

- 请求路径上的全链同步重算、jsonl 全文扫描（必须游标增量）。
- 无界缓存 key、无 TTL/LRU 的 Map。
- 面板各自为政的 setInterval 轮询（必须经统一数据层）。

## 三、落地路线（三步，渐进不推倒）

| 步 | 内容 | 状态 |
|---|---|---|

### 容器选型（已定稿 2026-09-03）：**Dockview**

- 选定理由：React 原生、活跃维护、零依赖；支持任意分栏/拖拽/tab 编组/浮动窗口/popout（远期多显示器直接复用）；布局可序列化 JSON 接持久化。
- 备选否决：Golden Layout（vanilla JS、React 集成需包装、维护偏老）；react-grid-layout 维持现状（网格吸附模型天花板，不支持自由分栏与 tab 编组）。
- 迁移口径：面板组件（01/05/06/07/08/09/10）不动，只换外层容器；`panel-registry.tsx` 注册表保留，演变为"可添加面板类型清单 + 每窗三要素（品种/周期/类型）"。
- **回退点**：迁移前已打 git 标签 `pre-dockview-backup`（commit f5678a2，2026-09-03），回退执行 `git checkout pre-dockview-backup` 或 `git reset --hard pre-dockview-backup`。

## 四、明确不做（本轮及近期）

- 不重写 grid 布局系统（react-grid-layout 继续用）。
- 不引入大型状态管理/图表框架。
- 不做多用户/权限体系（单机自用定位不变）。

## 五、风险与注意

- 面板独立 scope 后，01 总览这类"概览"面板语义要想清楚跟谁走（建议永远跟随全局档，或固定 all）。
- R1 扇出预算会让 ingest 路由耗时变长（多算 8 个 key），采集器 POST 超时要放宽，或改异步（入库即回 202，后台算）。
- 链接组的"周期不联动"默认值后续若交易员需要也可加成可选维度，store 设计时把链接维度做成配置项。

**验证**：`npx tsc --noEmit` 通过。
