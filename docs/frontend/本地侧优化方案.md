# 本地侧优化方案（BFF + 前端，可自主落地）

日期：2026-09-10；**2026-09-12 修订：L1~L5 与缓存分级已于 2026-09-11「首屏提速」全部落地**（版本驱动失效、调度器、双车道、IndexedDB 持久化、超时链对齐，详见 `../architecture/K线与期权数据周期管理与防堵塞设计.md` §八/§九）。本文保留作为各项措施的原始设计依据。状态：**已实施**。

**范围**：只改本仓（Next.js BFF `src/server/*` + Route Handlers + 前端 hooks/组件）就能生效的优化，
**不需要 Go 团队配合**。每一项都可独立上线、独立回滚。

**配套文档**：
- 需要 Go 服务端配合的部分 → [`../backend/服务端优化与更新策略.md`](../backend/服务端优化与更新策略.md)

## 0. 一句话结论

当前空态的**根因在传输层**（后端 TTFB 只有 2~6s，但 175KB 裸 JSON 以 1~3KB/s 慢传，极端时卡死 150s+），
本地侧改不了网络，但可以做到三件事：**让它没那么容易失败**（超时预算 + 缓存）、
**失败时别让用户看见空白**（陈旧兜底 + 脏更新）、**少发请求**（合并 + 闸门）。

## 3. 各项怎么做

### L1 脏更新：版本号驱动失效（✅ 2026-09-10 已落地）

**原问题**：`useSnapshotSync` 曾每 30s 轮询一个本地采集状态端点、拿它的版本字段做版本号；
该端点随旧采集链路删除后版本字段恒为 `null` → **invalidate 永不触发**。
而真实数据查询的 `refetchInterval` 是 `false`（只有 `local-demo` 才 60s 轮询），
于是"首屏失败 = 永久空态，只能手动 F5"。

**已实现**（`src/features/options/data-freshness.ts` + `src/app/api/options/version/route.ts`）：

1. 新增**极轻** BFF 路由 `GET /api/options/version`，返回体只有几百字节：

   ```json
   { "v": "GC:0dte:1789047000|GC:d30:1789047000|NQ:0dte:1789047000|...", "entries": [ ... ] }
   ```

   实现复用 `upstream("/options/status")`，只抽取 `(product, scope, unix)` 三元组，
   且**同一 (product, scope) 只保留最新 unix**（上游存在陈旧重复条目，见服务端文档 §2.2 问题 C）；
   走 BFF 既有的 10s 进程内缓存，多面板同时轮询也只有一份上游请求。

2. `useSnapshotSync` 改为打 `/api/options/version`，`v` 字符串变化 → `invalidateQueries()`。
   失效时排除版本查询自身，避免自激。

3. **保险丝**：同一版本下，若检测到存在处于 `error` 的查询，每次版本轮询（30s）重试一次 ——
   修掉"失败一次就永久空态"。正常有数据的查询不受影响，仍是同版本零重复请求。

**验收**：后端快照 unix 变化后 30s 内面板自动刷新；首屏失败后在后端恢复后 30s 内自动回填。
**回滚**：`data-freshness.ts` 单文件，还原即回到旧驱动方式（旧端点已不存在，故实际需一并回滚该页提交）。

### L2 陈旧兜底（stale-while-error）

两层保险，缺一层都不够：

- **BFF 层**（`go-options.ts`）：把缓存从"10s 后即弃"改成"**成功值 + 上次成功时间戳**"。
  upstream 抛错时，若存在上次成功值且未超过陈旧上限（建议 dashboard/levels 5 分钟、intraday 2 分钟），
  返回 `{ ...stale, stale: true, stale_age_sec }` 而不是抛错。前端据此显示"数据可能不是最新"角标。
- **前端层**：`useQuery` 加 `placeholderData: keepPreviousData`，
  并在 `isError && data` 时仍渲染旧数据 + 顶部提示条（不要整块替换成空态）。

**注意**：`sanitizePublicData` 会对整包做深拷贝（见 `src/lib/data-messages.ts`），
缓存要缓存**清洗后的结果**，避免每次重复遍历 900KB 结构。

**验收**：手动把 `OPTIONS_API_BASE_URL` 指到一个不存在的地址，面板应保留上一次数据 + 提示，而不是空白。
**回滚**：缓存分支加一个 `STALE_ON_ERROR=0` 环境变量开关即可关闭。

### L3 总预算超时 + 错误分层

- 把"每次 upstream 12s"改成"**整条路由一个预算**"：dashboard 25s、levels/intraday 35s。
  实现方式：入口处 `AbortSignal.timeout(budget)` 与上游 `AbortSignal.timeout(budget - 2s)` 组合，
  或直接用 `AbortSignal.any([routeSignal, ...])`（Node 20+ 支持）。
- 错误分三类，别再一律显示"当前暂无可用数据"：

  | 情况 | 文案方向 |
  |---|---|
  | 超时/连接失败 | 「行情服务响应较慢，正在重试」 |
  | 后端明确 `has_data=false` | 「该周期暂无数据」 |
  | 陈旧兜底 | 「显示 3 分钟前的数据」 |

  ⚠️ `data-messages.ts` 的 `INTERNAL_DATA_DETAIL` 正则含 `timeout|fetch|ECONN|接口|服务端|后端`，
  会把含这些词的原文全部替换成兜底文案 —— 所以**文案要靠错误码传递，不能靠 message 字符串**。
  现有代码用 `message` 传语义是个坑，本项需顺带修（给 `GoOptionsError` 加 `kind` 字段）。

**验收**：人为让后端慢时，看到的是"响应较慢"而不是"暂无数据"。
**回滚**：预算值提为环境变量，改回 12s 即恢复。

### L4 缓存分级 + 负缓存

现状 `go-options.ts:60` 统一 TTL 10s、失败即删缓存（`:62`）。改为：

| 接口 | 成功 TTL | 失败负缓存 | 陈旧上限 |
|---|---|---|---|
| `/options/status` | 30s | 5s | 10 分钟 |
| `/options/dashboard` | 20s | 5s | 5 分钟 |
| `/options/levels` | 20s | 10s | 5 分钟 |
| `/options/intraday` | 10s | 5s | 2 分钟 |
| `/options/chain` / `term` | 20s | 5s | 5 分钟 |

single-flight 逻辑保留（同 key 并发只打一次上游），只延长 TTL 并加负缓存。

### L5 underlying 解析缓存

`fixedOptionUnderlying()` 恒返回 `undefined`（`option-underlying.ts:2`）→
每次 `dashboard()` 都先打一次 `/options/status`（31KB，0.7~5.6s）解析合约。
改为按 `product` 缓存 60s（这个文件是死逻辑，改它不涉业务口径）。
**收益**：每个 dashboard 请求省掉一次完整往返，等价于把超时预算从 24s 变回 12s 的余量。

### L6 面板级并发闸门

8 个面板同时挂载会各自发起 upstream。加一个进程内信号量，
**同一 `product` 最多 2 路并发**打 Go，其余排队等缓存命中（配合 L4 的 single-flight，
排队的请求基本都能直接吃到前一次的结果）。
**收益**：把"8 路并发 × retry"压到 2 路，直接缓解自残式拥塞。

### L7 响应裁剪（BFF 侧投影）

Go 返回体偏大（dashboard d90/close 880~905KB、levels 24h 3.4MB）。BFF 转发前可做投影：
丢弃前端未消费的字段、heatmap cells 按视图窗口裁剪、levels 按 timeframe 降采样。
**注意**：这属于改数据契约，必须先核对 `src/api/options.ts` 的类型定义，
建议先用"白名单字段"方式小步做，且保留完整响应到 `?full=1` 便于排障。

### L8 前端显示缓冲

- 错误时**不清空** `data`（`keepPreviousData` + 面板层判空逻辑改成"有旧数据就渲染旧数据"）。
- 空态组件加**手动重试按钮**（现在只能整页刷新）。
- 重试策略：`retry: 1` 保留，但加指数退避（1s → 5s），并在连续失败 3 次后停止自动重试，转手动。

### L9 `days` 参数对齐

`src/api/options.ts:446` 写死 `days: days ?? 20`，绕过了服务端 `defaultDashboardDays`
（0dte=1 / d30=30 / d90=90 / close=45）。改为不传或按 scope 传默认值。
⚠️ 已实测：`days=1` 与 `days=20` 的响应体同为 177KB、耗时分布无差异 ——
**这一项不是性能问题，只是口径一致性问题**，顺手改即可，不要指望它提速。

### L10 状态徽标（✅ 已随旧采集链路删除）

`data-source-badge.tsx`（`DataSourceBadge` / `StatusDot`）读取的正是旧采集状态端点，
**且经核查无人 import —— 属死代码**，已随整个旧采集链路一并删除，
"顶栏长期显示数据尚未就绪"的问题因此消失，无需再改。若日后要恢复状态灯，
直接消费 `/api/options/version` 的 `entries[].unix` 判断新鲜度（口径见服务端文档 §2.1 实测周期）。

## 4. 关于"buffer"（单独说明）

用户提到的 buffer 在本地侧有三层含义，结论各不相同：

| 层 | 能不能靠 buffer 解决 | 说明 |
|---|---|---|
| Go → BFF 传输卡顿 | ❌ **不能** | 卡在字节流本身（1~3KB/s）。BFF 无论怎么缓冲都得等它传完。**只能靠后端开压缩**（见服务端文档 S1），或放宽超时等它 |
| BFF 内存缓冲 | ✅ **能** | 缓存整包响应对象（L2/L4），让后续请求不必再等传输；同时缓存 sanitize 后的结果省 CPU |
| 前端显示缓冲 | ✅ **能** | 保留上次成功数据作为显示缓冲（L8），传输失败时用户看到的是旧数据而不是白板 |

**一句话**：本地侧的 buffer 值在"复用"和"兜底"，不在"加速"。真正的加速在服务端压缩。

## 5. 建议实施顺序

```
✅ L1（脏更新 + 失败重试保险丝）  ← 2026-09-10 已落地，永久空态已修
✅ L10（旧状态徽标）             ← 2026-09-10 随死代码删除
 ↓
L3（超时预算 + 错误分层）  ← 最小改动，立刻消除"能返回却被掐断"
 ↓
L4 + L2（缓存分级 + 陈旧兜底）  ← 抖动时不再空白
 ↓
L5 + L6（解析缓存 + 并发闸门）  ← 减负
 ↓
L8（前端显示缓冲）  ← 体验收尾
 ↓
L9（days 对齐）  ← 顺手
 ↓
L7（响应裁剪）  ← 涉及数据契约，单独评审后再做
```

每步做完停一次、验一次，不跨步连做。

## 6. 边界（本方案不做的事）

- 不改 Greeks / GEX / 墙位计算口径。
- 不把 `source` 字段的掩码打开（`databento` 等字样属内部信息，按 AGENTS.md 既定边界保留）。
- 不引入 DataFusion / DuckDB / 私有二进制等替代方案（此前已明确拒绝）。
- 不在本轮做 WebSocket 全量替换（属服务端文档 S7 范畴）。
